# Панель KPI эксплуатации целевой архитектуры
Все значения ниже являются критериями приёмки. Для эксплуатации владельцы сохраняют временной ряд, профиль нагрузки и перечень инцидентов. Протоколы фактических испытаний появятся после внедрения.

| KPI | Цель | Измерение и инструмент | Бизнес-смысл |
|---|---|---|---|
| Доступность ядра, 24×7 | ≥99,95% за год | Внешние синтетические пробы регистрации заказа и оформления отгрузки из двух точек, результаты в Prometheus. Сверять с ошибками реальных операций и событиями восстановления. A = 100 × (секунды периода − длительность объединения интервалов недоступности ядра) / секунды периода. Включать плановые простои. Пробел мониторинга требует расследования. | За 365 дней допустимо суммарно 262,8 мин простоя. Измеряем возможность выполнить операцию, включая отказ шлюза. |
| Свежесть статусов в DWH | Каждый ключевой статус <5 с от commit до видимости, начиная с месяца 3 | Для каждого изменения сопоставить позицию источника с подтверждением видимости в DWH. Синхронизировать часы. max(t видимости − t commit) за окно. Ожидаемый статус без подтверждения за 5 с нарушает цель. Контрольные события в тихие периоды. В Grafana максимум, число просрочек и P99 для диагностики. | Диспетчер и холдинг видят отгрузки вовремя, пропавший статус не выпадает из отчёта. |
| Суточный объём | 500 000 отправлений за 24 ч | Считать уникальные ID зарегистрированных отправлений по журналу домена. Суточный прогон с неравномерным профилем и сверкой с входным набором. 500 000 / 86 400 ≈ 5,79 отправления/с в среднем. | Проверяет дневной объём работы сети, включая часы высокой активности. |
| Создание заказов в пике | 200 успешных созданий/с | Генератор k6 подаёт уникальные валидные заявки. Считать подтверждённые долговечные создания по секундным окнам и сверять ID после теста. Анализировать P99, ошибки и очередь при параллельном потоке GPS. Длительность пика согласовать с бизнесом. | Предотвращает очередь на оформлении и двойную регистрацию. |
| Запись телеметрии при отказе склада/биллинга | 3000 уникальных записей/с в пике, 0 потерянных событий после восстановления | Воспроизвести известный набор ID с повторами при отказе складских и финансовых потребителей. Измерить подтверждённые записи/с и разность множеств ID генератора и хранилища после дренирования очереди. Одновременно проверять KPI заказов и сравнить их задержку с контрольным профилем. | Сохраняется история движения груза без конкуренции за ресурсы ядра. |
| Потери ответов банка из-за timeout | 0% | В тесте оборвать соединение до и после фиксации уведомления. В эксплуатации сверять реестр банка с долговечным журналом по уникальному ID. 100 × число подтверждений банка, отсутствующих после согласованного окна сверки из-за тайм-аута / все ожидаемые уникальные подтверждения. Отдельный алерт на любой просроченный ID, нулевой знаменатель — нет наблюдений. | Оплата не исчезает из учёта, повторная доставка не ведёт к повторному списанию. |
| Инвариант EDI | 0 оплаченных счетов без подтверждённой отгрузки | Потоковая проверка истории саг по корреляционному ID в отдельной контрольной проекции. Инъекция дублей, перестановок, отмен резерва и тайм-аутов. При несогласованном состоянии остановить оплату и направить на сверку. | Защищает от платежа за отсутствующий товар. |

**Реакция.** Дежурный SRE отслеживает выгорание бюджета доступности и задержку старейшего события. Владелец соответствующего домена разбирает пропуски по ID. Ответственные за платежи и EDI приостанавливают повторное финансовое действие до сверки. При нарушении критериев на пилоте расширение волны откладывается.
